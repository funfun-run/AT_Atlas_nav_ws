condition_variable 内部机制 & Action Client 生命周期

第一部分：condition_variable 内部机制

1.1 为什么需要 condition_variable？

这个节点里有两个线程在跑，它们需要协作：

线程干什么执行的函数
服务线程 收到 FSM 的"走"指令，发 goal 给 Nav2，然后必须等导航结束才能返回响应 handle_go_next()
Action 回调线程 Nav2 导航结束后的通知在这里到达 result_callback()

矛盾在哪？ 服务线程必须"等"，但不能用忙等（死循环检查标志），那会浪费 CPU。也不能用 sleep()，因为不知道要等多久。

答案：操作系统提供的 condition_variable——让线程"睡"在某个条件上，条件满足时由另一个线程唤醒。睡的时候不占 CPU。

1.2 三个核心组件

组件类型作用
mtx_ std::mutex 互斥锁，保护 goal_done_ 和 goal_success_ 不被两个线程同时读写（数据竞争）
cv_ std::condition_variable 条件变量本体，提供 wait / notify 机制
goal_done_ bool 条件本身——"导航出结果了吗？"
关键关系：mutex 保护数据，condition_variable 传递"数据变了"的信号。两者总是一起出现，但职责不同。

1.3 cv_.wait() 内部发生了什么

这一行代码背后，内核做了很多事：

cv_.wait(lock, [this] { return goal_done_; });

等价的伪代码展开：

// cv_.wait(lock, predicate) 的内部等价于：
while (!predicate()) {              // ① 检查条件：goal_done_ == true？
    // 还没满足 → 需要睡觉等

    // ② 把当前线程加入 cv_ 的等待队列（内核操作）
    //    从"运行态"切换到"阻塞态"（不占 CPU）

    // ③ 释放 lock（原子操作：解锁 + 开始等待）
    //    必须释放，否则 result_callback 拿不到锁，永远无法设 goal_done_=true

    // ④ 线程在这里暂停 —— 不消耗任何 CPU 周期
    //    ... 可能等几毫秒，也可能等几分钟 ...

    // ⑤ 被 cv_.notify_one() 唤醒！重新获取 lock
    //    操作系统把线程从"阻塞态"切回"就绪态"，调度到 CPU 上
    //    重新获取 mutex（可能短暂等待 result_callback 释放锁）

    // ⑥ 循环回到 ①，重新检查条件
}
// 条件满足，wait 返回，lock 保持锁定状态

图解：wait 的原子操作链

服务线程 Action 回调线程 ──────── ────────────── unique_lock(mtx_) ✓ 已锁 cv_.wait(lock, pred): ├─ pred() → false ├─ 【原子操作开始】 │ ├─ 把自己挂到 cv_ 等待队列 │ ├─ 解锁 mtx_ ←─── 现在 result_callback 可以拿锁了！ │ └─ 线程阻塞 │ lock_guard(mtx_) ✓ 拿到锁了 │ goal_success_ = true; │ goal_done_ = true; │ cv_.notify_one(); │ ├─ 从等待队列取出服务线程 │ └─ 标记为"可运行" │ } // lock_guard 析构，解锁 mtx_ │ ├─ 【被唤醒】 ├─ 重新获取 mtx_ ✓ 已锁 ←─── 现在锁又回到服务线程手里 ├─ pred() → true （goal_done_ 已经是 true 了） └─ 返回，lock 保持锁定 success = goal_success_; // 安全：锁还拿着 } // unique_lock 析构，解锁

1.4 为什么要用带 predicate 的 wait？

等价写法对比：

// ❌ 不安全的写法（只用单参数 wait）
cv_.wait(lock);  // 可能被"虚假唤醒"——OS 无缘无故唤醒线程
success = goal_success_;  // 此时 goal_done_ 可能还是 false！

// ✅ 安全的写法（带 predicate）
cv_.wait(lock, [this] { return goal_done_; });
// 即使虚假唤醒，循环会再检查一次 goal_done_，不满足继续睡
C++ 标准明确允许虚假唤醒（spurious wakeup）。这是操作系统调度器的优化行为——提前唤醒线程以避免错过通知窗口。带 predicate 的 wait 自动处理了这种情况。

1.5 notify_one() vs notify_all()

函数唤醒谁适用场景
cv_.notify_one() 从等待队列中唤醒一个线程（任意选一个） 我们的场景：只有一个服务调用在处理
cv_.notify_all() 唤醒等待队列中所有线程 多个线程都在等同一个条件，如"系统状态变为 READY"
即使条件变量叫 notify_one，也不能假设"恰好有一个线程在等"。如果通知到达时没有线程在 wait，通知丢失——这就是为什么必须先设 goal_done_=true 再 notify，且 wait 进来先检查条件（如果通知已丢失，条件已经是 true，wait 直接返回不睡）。

1.6 lock_guard vs unique_lock

std::lock_guardstd::unique_lock
功能 构造时加锁，析构时解锁
不能手动 unlock，不能转移		 可以手动 lock/unlock
可以转移所有权
可以被 cv_.wait() 临时解锁
开销 更轻（只是一个 RAII wrapper） 多一个 bool 标志跟踪是否持有锁
我们的代码里 result_callback 中：进→改标志→出，简单路径 handle_go_next 中：需要传给 cv_.wait()（wait 要求 unique_lock）

第二部分：Action Client 生命周期

2.1 什么是 Action？

ROS2 有三种通信方式：

方式模式适用场景
Topic发布/订阅，单向流传感器数据、速度指令
Service请求/响应，一问一答快速操作：开关灯、查状态
Action目标→反馈→结果，可取消长时间任务：导航、机械臂运动

Nav2 的导航是典型的 Action 场景：发一个目标点，导航过程中持续收到进度反馈（剩余距离），最终收到结果（到达/失败/取消）。整个过程可能持续几十秒甚至几分钟。

2.4 生命周期各阶段详解

1
创建 Client 
action_client_ = rclcpp_action::create_client<NavigateToPose>(
    this, "navigate_to_pose");

告诉 ROS2："我要用 navigate_to_pose 这个 action"。
此时还没有和 Nav2 建立连接，只是一个本地代理对象。
底层：发起 ROS2 的 action 服务发现（类似 topic 的 publisher/subscriber 匹配）。

2
等待 Server 上线 
action_client_->wait_for_action_server(std::chrono::seconds(10));

阻塞等待 Nav2 的 action server 注册到 ROS2 图上。
返回 true：连接建立，可以发 goal。
返回 false：超时，说明 Nav2 没启动。

这个调用是同步阻塞的——当前线程会卡在这里最多 10 秒。
所以放在构造函数里合适：反正初始化阶段没别的事要做。
3
异步发送 Goal 
action_client_->async_send_goal(goal_msg, opts);

async 意味着这个调用立即返回，不等待导航完成。
它返回一个 future，但我们不拿它——回调已经绑在 opts 里了。

底层发生了什么：

  1. 序列化 goal_msg → 发给 Nav2 的 action server
  2. Nav2 接受 goal 后回调 goal_response_callback（我们没绑这个，因为 result_callback 已经覆盖了"是否被拒"的判断）
  3. Nav2 开始规划+控制，定期发送反馈 → 触发 feedback_callback
  4. 导航结束 → 发送结果 → 触发 result_callback
4
Client 复用

同一个 action client 对象可以多次调用 async_send_goal()——每次发新 goal 就行。
不需要重建。async_send_goal 返回后，旧的 GoalHandle 和新的独立存在。

前提是上一个 goal 已经出结果。如果上一个还在执行中又发新的，Nav2 默认会抢占——取消旧目标，执行新目标。这个行为由 Nav2 的 BT navigator 决定。
5
Client 销毁

Node 析构时会自动清理 action client。如果还有 goal 在执行中，会发送取消请求。
不需要手动 destroy_client()，SharedPtr 的引用计数归零即析构。

2.5 GoalHandle 的作用

ClientGoalHandle 是"一次导航任务"的句柄。它的生命周期是：
async_send_goal 创建 → result 回调后仍存活（回调参数是它的引用）→ 回调返回后销毁。

通过 GoalHandle 可以：

  • 查询 goal 状态（ACCEPTED / EXECUTING / SUCCEEDED / ABORTED / CANCELED）
  • 主动取消（async_cancel_goal(goal_handle)）
  • 获取 goal_id（唯一标识）

我们的代码里只用了 result 回调的参数（它包含了 GoalHandle 和 result），没有存 GoalHandle 的引用——因为不需要取消功能。

2.6 回调线程模型

这是初学者最容易踩的坑：action 的回调在哪个线程执行？

rclcpp::spin(node) ← 主线程 │ ├──► 检查服务请求队列 ──► 有请求 ──► 【线程池线程】执行 handle_go_next() │ ├──► 检查 action 反馈队列 ──► 有反馈 ──► 【线程池线程】执行 feedback_callback() │ └──► 检查 action 结果队列 ──► 有结果 ──► 【线程池线程】执行 result_callback()

关键结论：

  • handle_go_next() 和 result_callback() 在不同线程中执行
  • 它们共享 goal_done_、goal_success_ —— 所以必须用 mutex 保护
  • spin() 在主线程中，负责分派消息到回调。服务回调虽然阻塞，但它在独立线程，不影响 spin 分派 action 回调
如果不用条件变量，而是这样写会怎样？ 
// ❌ 死循环忙等
while (!goal_done_) { /* 空转 */ }
// 问题：while 循环抢占了 CPU，spin 得不到调度，result_callback 永远不会被调用
// → 死锁！goal_done_ 永远为 false
// ❌ 用 sleep
while (!goal_done_) { std::this_thread::sleep_for(100ms); }
// 能工作但很差：延迟 100ms，高频反馈场景完全不合适

第四部分：常见问题

Q1: 如果 Nav2 导航失败（ABORTED），服务会返回什么？

response->success = false，response->message = "导航失败"。
FSM 可以据此决定：重试当前点、跳过当前点、或切换到遥控模式。

Q2: 如果在 wait 期间又收到一个服务调用会怎样？

ROS2 服务默认使用线程池处理请求。如果上一个 handle_go_next() 还在 wait，新请求会在另一个线程池线程中执行新的 handle_go_next()——两个线程同时操作 current_index_ 和 action_client_，会导致数据竞争。

当前代码的保护：服务是串行调用的——FSM 知道要等响应回来再调下一次。如果 FSM 被错误地连续调两次，会有并发问题。生产代码应加 std::atomic<bool> busy_ 或使用互斥锁保护整个 handle_go_next()。

Q3: feedback_callback 需要加锁吗？

不需要。它只读 feedback->distance_remaining，不读写任何共享成员变量。get_logger() 本身是线程安全的。

Q4: 为什么 result_callback 不用 unique_lock？

因为它不需要传给 cv_.wait()（那是服务线程的事），也不需要手动 unlock。lock_guard 更轻量：没有额外的 bool 标志，调用栈更小。能用 lock_guard 就不用 unique_lock——这是 C++ 最佳实践。
